# pgvector RAG retrieval demo with an evaluation harness

A small, end-to-end retrieval stack on **Postgres 17 + pgvector**, built to answer one question
honestly: *given a support knowledge base, which retrieval strategy actually finds the right
article, and how do we know?*

* **Corpus** — 48 synthetic field-service articles (appliance troubleshooting, error codes,
  warranty and dispatch policy). Synthetic on purpose: no confidential content, and every
  question has a known correct answer.
* **Retrievers** — three over the *same* table:
  * `vector`   — cosine similarity on a `vector(384)` column with an HNSW index (`bge-small-en-v1.5`, CPU/ONNX, no API key)
  * `fulltext` — Postgres `tsvector` + `ts_rank_cd`, GIN index, query lexemes OR-ed
  * `hybrid`   — Reciprocal Rank Fusion of the two
* **Evaluation** — 36 labelled questions in three kinds (`code`: exact error codes, `paraphrase`:
  customer wording that shares few words with the article, `policy`: process questions).
  Metrics: Recall@1/3/5 and MRR@5, overall and per kind. Output: `eval/results.md`.

## Run

```bash
./scripts/up.sh            # docker (pgvector/pgvector:pg17 on :5433) + venv + ingest + eval
.venv/bin/python -m rag.search "fridge light on but warm inside"   # ad-hoc query, all 3 retrievers
.venv/bin/python -m pytest -q                                      # chunking + RRF unit tests
```

## Results (current run)

| retriever | R@1 | R@3 | R@5 | MRR@5 |
|---|---|---|---|---|
| vector | 0.97 | 1.00 | 1.00 | 0.99 |
| fulltext | 0.83 | 0.97 | 1.00 | 0.91 |
| hybrid | 0.89 | 1.00 | 1.00 | 0.94 |

Per kind is in `eval/results.md`. What the numbers say, and what they do not:

* On 48 documents a good embedding model is close to a ceiling; the eval is too small to rank
  vector vs hybrid with confidence. **The harness is the point**, not this particular table.
  The same script runs unchanged when the corpus is 50,000 manual pages.
* Full-text lost mostly on `paraphrase` questions ("cookies burn on the bottom" vs. an article
  about oven calibration). That is exactly the class of query a symptom-driven support tool sees.
* Hybrid (plain RRF, equal weight) was *slightly worse* at R@1 than vector alone here, because
  full-text's weaker ranking gets an equal vote. Two fixes I would test next, in order:
  weighted RRF (e.g. 0.7/0.3), or using full-text only as an exact-token booster for codes and part
  numbers. Both are one-line changes in `rag/search.py` and the eval will tell us if they help.
* The first version of `fulltext` used `websearch_to_tsquery`, which ANDs terms and returned
  nothing for most symptom queries (R@5 = 0.14). Switching to OR-ed lexemes fixed it. **Without
  the eval set that bug would have shipped** — the code ran fine and returned plausible rows.

## Design notes

* **Why Postgres for both** — one database, one backup, one access-control model, transactional
  writes alongside the business data. For a corpus that fits in one node, a separate vector store
  adds an operational surface without adding recall.
* **Query prefix** — bge models expect an instruction prefix on the query side only
  (`rag/embed.py`). Forgetting it costs measurable recall; the eval catches that too.
* **Chunking** — sentence-window with one-sentence overlap (`rag/chunk.py`). Articles here are
  short so most are one chunk; the function exists so long manuals go through the same path.
* **Document-level dedupe** — retrievers return the best chunk per document because labels are
  per document. For generation you would pass the top chunks, not the top documents.
* **Not included** — the generation step. Retrieval is where most RAG failures originate, so it is
  evaluated first and separately. Plugging an LLM in is a function that takes the top-k chunks;
  its eval (faithfulness, answer correctness) is a second harness with a judged rubric.

## Layout

```
corpus/build_corpus.py   writes corpus/docs.jsonl (48 synthetic articles)
eval/questions.jsonl     36 questions with gold doc ids and a kind label
eval/results.md          generated by rag.evaluate
rag/db.py                DSN, schema (tsvector generated column, HNSW + GIN indexes)
rag/embed.py             bge-small via fastembed; query prefix
rag/chunk.py             sentence-window chunker
rag/ingest.py            chunk -> embed -> insert
rag/search.py            vector / fulltext / hybrid (RRF)
rag/evaluate.py          Recall@k, MRR@5, per kind, misses table
tests/                   chunking + RRF
```
